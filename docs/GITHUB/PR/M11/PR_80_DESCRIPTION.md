# PR: Bookable appointment slots that share each queue's daily limit with walk-ins (Issue 80 / M11-80)

**Milestone:** [Milestone 11: Appointments, Check-in & Patient Care Extras](https://github.com/Billykat7/clinicQ/milestone/11) ·
**Issue:** [#80](https://github.com/Billykat7/clinicQ/issues/80) · **Builds on:** #24 (hours, holidays, closures), #25
(queues and `max_daily_capacity`), #26 (services), #39 and #40 (the ticket counter and the join service), all merged ·
**Unblocks:** #81

A chronic patient collecting a repeat script should hold a time, not stand in the 07:30 line. With this PR:

- **A clinic manager sets up a queue's appointment book:** weekly windows ("Thursdays 08:00 to 10:00, 30-minute
  slots, two patients each"), one-date overrides (including "no appointments on the 5th"), and how far ahead and how
  late the clinic takes bookings.
- **Slots are generated from that book.** Public holidays, announced closures and the hours the clinic is shut give
  no slots, whether generated by the manager or by the new nightly sweep. Generating twice changes nothing.
- **Appointments and walk-ins share one daily limit per queue.** A queue that sees 40 patients a day still sees 40,
  however many booked and however many walked in. The count lives in one place.
- **A slot cannot be overbooked, and the database is what refuses it.** Two sessions booking the last place at once
  get one booking and one "That time is fully booked", on a real PostgreSQL.
- **A manager blocks a range for a staff absence.** Those slots stop being offered at once and come back when the
  block is lifted.

**Not in this PR (by the issue's scope):** booking by a patient, rescheduling, cancelling from a screen and turning a
booking into a ticket are Issue 81. This PR ships the storage primitive they stand on (`claim_place` and
`release_place`), the way #39's `issue_ticket` came before #40's `join_queue`. There is no staff screen for the book
yet: the API is the surface, documented in `contracts/appointments.yaml`.

## Summary

- **The model** (`src/database/models/appointment_slot.py`, migration `0039`):
  - `appointment_policy`: a clinic's `horizon_days` (default 28) and `min_lead_minutes` (default 60).
  - `appointment_template_window` and `appointment_day_override`: the week and one date's windows.
  - `appointment_slot`: `starts_at`, `ends_at`, `service_day`, `capacity`, `booked_count`, `withdrawn_at`.
    `ck_appointment_slot_not_overbooked` (`booked_count <= capacity`) and `uq_appointment_slot_queue_start`.
  - `appointment_block`: a range, optionally one queue, a reason for staff, `lifted_at`.
  - `appointment`: one place held by one patient (`booked` or `cancelled`).
  - `queue_capacity_day`: the lock row for one queue's day. It holds no figures.
- **Planning** (`src/modules/appointments/schedule.py`, pure): `plan_slots(plan, opening, first_day, last_day)` cuts
  windows into slots and keeps only those the clinic is open for the whole of, through #24's `open_periods`.
- **Capacity** (`capacity.py`): `lock_day`, `day_usage` (tickets not cancelled plus booked places), `day_is_over`
  (for a join or a transfer), `claim_place` and `release_place`. Refusals are `SlotRefusedError`, 409
  `appointments.slot.<reason>`.
- **Whether a slot is on offer** (`availability.py`, pure): `refusal_for(slot, context)` returns one `SlotRefusal`:
  `withdrawn`, `blocked`, `closed`, `too_soon`, `too_far`, `slot_full`. The day view adds `day_full`.
- **The book** (`service.py`): policy, windows, overrides, `generate_slots` (a reconciliation), blocks, the day view,
  and `generate_published` for the sweep.
- **The API** (`router.py`, 11 operations under `/api/v1/sites/{site_id}/appointments`): policy GET/PUT, template
  GET/PUT, day override PUT/DELETE, `slots/generate`, `availability`, blocks GET/POST/DELETE. Every change is audited
  (`appointment_schedule`, `appointment_block`).
- **RBAC** (`rbac_manifest.py`): `appointments`, queue-shaped. The receptionist and nurse have `read · assigned`, the
  clinic manager `update · assigned`, the platform admin `read · business`.
- **The join service and transfers** now ask `capacity.day_is_over` instead of counting tickets themselves.
- **The nightly sweep** (`src/core/scheduler.py`): `run_appointment_slot_generation` at 02:30 SAST under advisory
  lock 880. It covers publicly listed clinics only.

## Design notes

**One place counts the day, under one lock.** The limit could be broken by two different races: two walk-ins, which
#39's counter lock already serialises, and a walk-in against a booking, which nothing did. Both paths now take the
same row lock, `queue_capacity_day(queue_id, service_day)`, before counting. The row is taken with an
`INSERT … ON CONFLICT DO UPDATE` that changes nothing, so a day with no ticket yet (a booking three weeks out) still
has a row to lock. The lock order is fixed, so the paths cannot deadlock: a join takes the ticket counter and then
the day; a booking takes the day and then the slot. The row holds no count: the count is read live from tickets and
bookings, so a cancellation frees its place with nothing to drift.

**The slot's own guard is one statement and a constraint.** `UPDATE appointment_slot SET booked_count = booked_count
+ 1 WHERE id = … AND booked_count < capacity AND withdrawn_at IS NULL`. On PostgreSQL the loser of a race waits on the
row and re-checks the `WHERE` against the winner's committed row, so it updates nothing and is told the slot is full.
`ck_appointment_slot_not_overbooked` refuses an overbooked row whatever writes it. The PostgreSQL test proves this
with a hand-written update (the negative control).

**Slots are generated rows, not computed on the fly.** A place held has to be a row something can lock, count and
constrain. Generation is therefore a reconciliation, safe to run any number of times:
- a new time is created;
- an existing slot is kept and updated, but its capacity never drops below the places booked;
- an unbooked future slot the schedule no longer produces is deleted;
- a booked one is **withdrawn**: it is no longer offered and its bookings stand (reaching those patients is #81's);
- a withdrawn slot produced again is offered again;
- slots that have started are never touched.

**Holidays and closures are asked twice.** Generation skips what #24's schedule says is shut. The day view asks
again at read time, so a closure announced after generation hides the slots at once, without regenerating.

**Midnight.** A window whose end is at or before its start crosses midnight, like an opening span. A slot belongs to
the Johannesburg date it starts on, so Monday's 23:00 to 01:00 window gives Tuesday its 00:00 and 00:30 slots, and
they count against Tuesday's limit, like a ticket issued at 00:30. Two touching opening spans (a 24-hour clinic has
one per day) are merged before a slot is checked, so a 23:45 to 00:15 slot is open. A block or datetime sent without
an offset is read as Johannesburg time, as the API documents.

**The nightly sweep reads only listed clinics.** It acts for no one, so it has no `SiteAccess`. It reads through
`published_select`, the patient-facing guard, rather than an unscoped query with an exception entry. A clinic still
being checked cannot be booked by a patient anyway, and its manager can generate by hand. The service takes a
`RowSource` (`staff_rows(access)` or `published_rows(site_ids)`), so the rules are written once for both callers.

**A block counts the bookings it covers and does not cancel them.** `booked_places_inside` tells the manager that
patients are affected. Telling and moving those patients needs the booking flow (#81).

## Acceptance criteria

- [x] **Slots generate correctly from a weekly template including holiday exclusions:** a month of Thursdays skips
  Heritage Day on PostgreSQL, and 29 of 30 days are generated over HTTP. Closures and closed hours are excluded the
  same way, and regeneration is idempotent.
- [x] **A slot cannot be overbooked beyond its capacity, proven under concurrent booking:** two sessions give one
  booking and one `slot_full`, with the loser seen waiting on the lock. Twenty sessions on three places give exactly
  three. The check constraint refuses a hand-written overbooking.
- [x] **Appointment capacity and walk-in capacity are reconciled against one daily limit:** `capacity.py` is the one
  count, used by joins, transfers and bookings under one lock. In the 16-way race exactly the remaining 4 places were
  taken. Over HTTP, booked places refuse walk-ins and walk-ins refuse bookings.
- [x] **Availability reflects a cancellation within seconds:** nothing is cached. The released place shows on the
  very next read of the day view.
- [x] **Slot times respect `Africa/Johannesburg` across a DST-free but midnight-crossing test:** unit and HTTP tests
  run with `TZ=UTC`. 00:00 and 00:30 SAST belong to the next service day and are returned as `+02:00`.
- [x] **A clinic manager can block a slot range for a staff absence:** `POST /appointments/blocks` hides the slots at
  once, only a manager may do it (403 for the desk), it is audited, and lifting it brings them back.

## Risk and rollback

- **The join path takes one more lock**, only for a queue with a daily limit: the day row, right after the counter
  row that already serialises joins on that queue. A queue without a limit takes no extra lock. The full queue suite
  passes on PostgreSQL, including its 100-join concurrency test.
- **A queue's limit now counts booked places.** Until #81 lets patients book, nobody holds a place, so walk-in
  behaviour is unchanged in practice.
- **The nightly sweep does nothing for a clinic with no windows**, which today is every clinic.
- **Rollback:** revert, then `alembic downgrade 0038`, which drops the seven tables. Tickets are untouched.
