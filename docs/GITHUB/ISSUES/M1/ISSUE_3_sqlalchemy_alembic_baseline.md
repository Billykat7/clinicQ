## Context

Every model in the project hangs off this issue. It establishes the async SQLAlchemy 2.x engine and
session dependency, the declarative base with shared mixins, and the Alembic baseline that enables the
PostGIS extension; enabling it later in the migration chain would break a fresh database rebuild.

## Starting point

- Most of this exists: sync and async sessions (`get_db`, `get_async_db`) in `src/database/session.py`, a constraint naming convention in `src/database/models/base.py`, mixins in `src/database/models/mixins/`, and a baseline (`alembic/versions/0001_baseline.py`) that already runs `CREATE EXTENSION IF NOT EXISTS postgis WITH SCHEMA public`.
- The spec assumes async everywhere; the kernel serves most requests through the sync session. Pick one convention for new modules; see [open decisions](../README.md#open-decisions).
- **Decided (decision 5):** new modules use the sync `get_db`; `get_async_db` only for long-lived or streaming handlers. Alembic stays on the sync engine, so "configured for async" below does not apply.
- What is left: confirm each acceptance criterion with a test, especially the downgrade round-trip and the empty autogenerate diff.

## Scope

- Async engine and `async_sessionmaker`, plus a `get_session()` FastAPI dependency with correct teardown
- `Base` declarative class with `id`, `created_at`, `updated_at` and soft-delete mixins
- Alembic configured for async, with a baseline revision that runs `CREATE EXTENSION IF NOT EXISTS postgis`
- Naming conventions for constraints and indexes so autogenerated migrations are stable and reviewable
- A test fixture that creates and tears down a schema per test session

## Out of scope

- Any domain table (Issues 23, 25 and 39 add the first ones).
- Test factories (Issue 8).

## Acceptance criteria

- [ ] `alembic upgrade head` on an empty database succeeds and installs PostGIS
- [ ] `alembic downgrade base` then `upgrade head` round-trips without error
- [ ] Autogenerate produces a clean (empty) diff immediately after an upgrade
- [ ] The session dependency rolls back on an exception and never leaks a connection
- [ ] Tests run against a real PostGIS database, not SQLite
- [ ] Constraint names follow the documented convention in every generated migration

## How to verify

1. `make migrate-up` on an empty database, then `make migrate-down` and `make migrate-up` again: no errors.
2. `alembic revision --autogenerate` straight after an upgrade produces an empty migration.
3. `SELECT extname FROM pg_extension;` lists `postgis`.
